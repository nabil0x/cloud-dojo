Q3.4 — Wire an event trigger (30 XP)

Phase: Phase 3 — Lambda Container Images

Concept

Calling a function by hand is a demo; reacting to events is the point.

An event source mapping connects a service like SQS to your function, so messages arriving in the queue trigger invocations automatically with no server in between.

S3 can do the same: an object-created event invokes the function with details about the new object.

You wire dojo-queue (or an S3 event) to your function, then send a message or upload a file and prove the code ran through logs or a DynamoDB write.

This is serverless in its natural state: events in, code runs, state goes to a store, and you never touch a machine.

Uses

  • Processing uploaded files the moment they land in S3.
  • Consuming a queue of background jobs without running a worker server.
  • Reacting to application events across services with no polling code.
  • Building event-driven pipelines where each step triggers the next.
  • Decoupling producers from consumers so each side scales on its own.

Key info

  • SQS mapping: aws --endpoint-url http://localhost:4566 lambda create-event-source-mapping --function-name dojo-lambda --event-source-arn <queue-arn>
  • Then send a message to dojo-queue and watch the function fire.
  • S3 route: configure a bucket notification that invokes the function on object creation.
  • Prove it fired via the emulator's container logs or a conditional write to DynamoDB.
  • Batch size and a dead-letter queue are how real mappings handle failures.
  • Check the mapping state: aws --endpoint-url http://localhost:4566 lambda list-event-source-mappings
  • Mappings are asynchronous; a failed batch can retry or land in a dead-letter queue.
  • LocalStack supports SQS triggers, which is why this phase runs smoothest there.
  • The S3 route needs a bucket notification configuration plus permission for S3 to invoke the function.

Pitfalls

  • Forgetting the execution role needs permission to read the queue or write to DynamoDB, which fails on real AWS.
  • Expecting exactly-once delivery. SQS can deliver a message twice, so handlers must be idempotent.
  • Wiring a trigger and never checking logs, so a function that errors looks like nothing happened.

Done check

paste the trigger evidence (log line or the written item).
