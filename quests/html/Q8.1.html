Q8.1 — Design doc + cost estimate (30 XP)

Phase: Phase 8 — RAG Capstone

Concept

The capstone is not a new service; it is judgment. Before any code, you write DESIGN.md: what the system is, how a request flows through it, and what it will cost. A grounded chatbot over your own documents moves data one way (documents into S3, indexed into a knowledge base) and requests another (client to gateway to function to retrieval to model and back). Drawing the boxes and arrows first forces every choice to have a one-line justification.

The cost table is the discipline that separates a demo from a system: unit economics at 100, 10k, and 1M requests. Systems that are cheap at 100 requests and ruinous at a million are the norm, so you need to know which one yours is before you build it.

The review is part of the quest, not ceremony.

Uses

  • Scoping: a diagram shows what is in and out before code sprawls.
  • Cost literacy: per-request token math makes spend predictable, not surprising.
  • Design review: reviewers critique a page, not a running system.
  • Onboarding: a new teammate reads the doc to understand the whole build.
  • Portfolio: a clear design doc is what interviewers actually read.

Key info

  • DESIGN.md sections: overview, architecture diagram (boxes plus arrows), service choices with one-line justifications, cost table, failure notes.
  • Cost table needs three scale rows:

| Scale | Requests/mo | Model tokens | Retrieval | Storage | Est. monthly |

|---|---|---|---|---|---|

| Small | 100 | ... | ... | ... | ... |

| Medium | 10k | ... | ... | ... | ... |

| Large | 1M | ... | ... | ... | ... |

  • Price the moving parts: model input and output tokens, knowledge base and endpoint hours, S3 storage, Lambda and API Gateway requests.
  • For every arrow, write why it exists ("SQS between API and indexer because ingestion spikes at upload"). If you cannot justify an arrow, delete the box.
  • Get the doc reviewed, then paste it as part of the quest.

Pitfalls

  • Skipping the cost table. The estimate is the deliverable, not decoration.
  • Arrows with no justification, which hide design debt until it breaks in the demo.
  • Estimating only the happy path and ignoring retries, token growth, or idle endpoint hours.
