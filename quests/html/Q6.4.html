Q6.4 — Multi-resource apply (35 XP)

Phase: Phase 6 — Terraform IaC

Concept

Real infrastructure is many resources wired together, and Terraform is built for exactly that. You can express an entire stack in one config, and a single apply builds it in the right order. Terraform reads the references between blocks (a subscription pointing at a topic's ARN) and builds a dependency graph, so it creates the topic before the subscription without you writing a sequence.

This quest grows the config to an SNS topic, a DynamoDB table, and an SQS queue with a subscription, which is the Phase 1 stack declared declaratively instead of clicked. Then you deliberately break one attribute and watch plan catch the problem before anything deploys.

That is the payoff: mistakes surface as a diff, not as a broken environment.

Uses

  • Full-stack provisioning: one apply builds messaging, storage, and a database together.
  • Environment parity: every environment gets the identical wiring from the same file.
  • Safe changes: plan shows the blast radius of an edit before you commit to it.
  • Destroy-and-rebuild: the whole stack can be torn down and recreated from code.
  • Reviewable changes: teammates read the plan diff in a pull request.

Key info

  • Wire four resources with implicit dependencies:

resource "aws_sns_topic" "dojo" { name = "dojo-topic" }
resource "aws_sqs_queue" "dojo" { name = "dojo-queue" }

resource "aws_sns_topic_subscription" "dojo" {
  topic_arn = aws_sns_topic.dojo.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.dojo.arn
}

resource "aws_dynamodb_table" "dojo" {
  name         = "dojo-table"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "id"
  attribute {
    name = "id"
    type = "S"
  }
}
  • Apply complete! Resources: 4 added counts what landed.
  • To force the caught plan, change an attribute on purpose (for example the table hash_key) and run plan.
  • References like aws_sns_topic.dojo.arn create the dependency edges automatically.

Pitfalls

  • Changing a force-new attribute by accident and getting a destroy plus recreate instead of an in-place update.
  • Not reading the plan when the stack grows, so an unexpected replace slips through.
  • Duplicating resource names across blocks, which causes apply conflicts in the emulator.
