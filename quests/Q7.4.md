# Q7.4 — Fargate service, live (35 XP)

**Phase:** Phase 7 — CI/CD + ECS

## Concept
ECS runs containers without you managing servers when you use the Fargate launch type. The vocabulary nests cleanly: a cluster is a logical pool, a task definition is the versioned blueprint (image, CPU, memory, env, logging), a service keeps a desired count of tasks running, and a task is one running instance of that blueprint. Fargate is serverless containers: no EC2 hosts to patch, and you pay per vCPU and GB-second while tasks run.

Two IAM roles quietly matter here. The execution role lets ECS pull the image and write logs; the task role is what the running code may call.

This quest stands up a cluster, a task definition sized at 0.25 vCPU and 0.5 GB, and a one-task service, then reaches the live container over HTTP.

## Uses
- Managed containers: ship an image and let the platform keep it running.
- Right-sized workloads: set CPU and memory per task without provisioning servers.
- Service discovery of health: a service replaces tasks that fail their checks.
- Central logs: the `awslogs` driver streams container output to CloudWatch.
- Repeatable deploys: task definition revisions make rollouts explicit and reversible.

## Key info
- Stand up the service:

```bash
aws ecs create-cluster --cluster-name dojo
aws ecs register-task-definition --cli-input-json file://taskdef.json
aws ecs create-service --cluster dojo --service-name dojo-svc \
  --task-definition dojo --desired-count 1 --launch-type FARGATE
aws ecs describe-services --cluster dojo --services dojo-svc \
  --query 'services[0].{running:runningCount,status:status}'
```

- `taskdef.json` carries the image, `cpu: "256"`, `memory: "512"`, the execution role, and a `logConfiguration` using the `awslogs` driver.
- The service's task needs a security group that allows inbound traffic on your app port.
- Hit the running task on its public IP or ENI: `curl http://<ip>:8000/health` and `curl http://<ip>:8000/s3`.
- Decide and note whether `/s3` points at real sandbox S3 or a stub.

## Pitfalls
- Forgetting the execution role, so the task cannot pull the image and dies immediately.
- A security group that blocks the app port, so the task runs but nothing can reach it.
- No `logConfiguration`, so a crashing task leaves you with no logs to debug in CloudWatch.
