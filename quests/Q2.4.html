Q2.4 — Seed on demand (25 XP)

Phase: Phase 2 — Compose Capstone

Concept

A fresh emulator is empty, which makes every later quest start from an unknown state.

The shared/seed.sh script fixes that by creating the bucket, queue, and table your quests expect.

You run it from the host, where the emulator is reachable at http://localhost:4566, and it uses the AWS CLI with the local endpoint to create those resources.

Once seeded, curl localhost:8080/s3 should list dojo-bucket, proving the app can see resources created out-of-band by a different client.

The deeper idea is infrastructure-as-script: instead of clicking around a console, you run a repeatable script that returns the environment to a known baseline.

That habit is exactly what grows into Terraform later in the course.

Uses

  • Resetting a dev environment to a known baseline before tests or a demo.
  • Sharing a "here is the initial state" script so teammates start from the same place.
  • Practicing the AWS CLI --endpoint-url pattern that works against any environment.
  • Building the instinct that repeatable setup beats manual clicking.
  • Creating fixtures that later automated tests can rely on.

Key info

  • Seed from the host, with the stack already up: bash ../shared/seed.sh
  • Verify through the app: curl localhost:8080/s3
  • The script targets the emulator using the AWS CLI's --endpoint-url http://localhost:4566.
  • Expected result: the response lists dojo-bucket.
  • Re-run the seed any time the emulator was recreated or you are unsure of the current state.
  • List buckets directly to double-check: aws --endpoint-url http://localhost:4566 s3 ls
  • The seed is safe to re-run; creating an already-existing resource is harmless in the emulator.
  • Keep the script in version control so the baseline travels with the repo.

Pitfalls

  • Running the script from inside a container, where localhost:4566 points at the wrong place. Seed from the host.
  • Seeding before docker compose up, so the emulator is not listening yet.
  • Assuming the bucket still exists after a down -v. The volumes are gone, so re-seed.

Done check

paste the /s3 response showing the bucket.
